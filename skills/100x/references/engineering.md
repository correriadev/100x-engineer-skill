# Engineering workflow

Use one construction path and one coordinated review for a feature, fix, test or procedure.
Explicit user and host instructions take precedence, including permissions and model availability.

## Select the path

- **Direct:** The user asks for a small or otherwise bounded change, check authoring or execution of an existing procedure without a formal plan or QA acceptance. No map or change contract is required. Inspect read-only, then present the expected outcome, edit scope, target, preconditions, permitted effects and verification before the first write or procedure with effects; continue in the same run. For behavior changes observe a meaningful focused RED before GREEN when applicable. Check authoring proves the check observes its intended failure; execution-only does not edit files. Report what ran, changed and remains unknown. Do not claim formal QA acceptance.
- **Planned:** The user supplies or asks for a plan, change ID or formal acceptance. Use the New Scope and QA contracts below. Missing, stale or inconsistent contracts block affected work; never silently fall back to direct mode.

Prefer the simplest complete solution across implementation, verification, operation and maintenance. Justify new dependencies or abstractions by current needs, material risks or costly-to-change boundaries. Preserve observable compatibility and inspect affected consumers. Prioritize required outcomes, consequential risks and uncertainty while respecting real prerequisites. Expand investigation only when it can change the decision or expose a material risk; do not infer performance or cost improvements from counts of tokens, tasks or tests.

## Ground the work

Use an existing suitable Project Mapper graph as a source-backed index, not as runtime proof. For example, `100x workbench mapper . --offline coverage --summary`. Check its snapshot, graph identity, coverage and gaps; reopen decisive current source, tests and configuration before claims or edits. Use `--expect-revision` when the target commit is known. If the graph or compatible tool is missing, stale, incomplete or unreadable, use `docs/README.md` and relevant docs, then manifests and current source. A map is optional for a small change. Do not map or refresh without a request. A requested refresh targets the stated committed snapshot; uncommitted work needs an explicit worktree map. Static extraction reuse can be incremental, while semantic evidence reuse is conservative when mapped inputs change. Preserve investigations and user-owned artifacts.

## Plan once

New Scope owns `docs/specs/<change-id>/context.sqlite`: intended behavior, acceptance criteria, risks, decisions, provenance, unresolved questions and planned versus observed information. `SCOPE.md` is its generated projection. Use the New Scope skill and `100x workbench scope` to validate, render and export the current revision. Put execution-relevant priority and rationale in task content: arbitrary task details are not exported and IDs are not business priority.

Plan QA obligations in the same planning flow using the QA Scope contract. Record the risk and failure to detect, preconditions, stimuli, lowest faithful test level, authoritative observations and assertions, environment, correlation and timing when material, artifacts and blocking status. Choose integration or end-to-end observation when a unit check cannot establish the effect. Publish `qa.json.contract` before relevant construction, then publish New Scope's revision-bound task projection through `100x workbench execute`. Keep `tasks.json` as the execution plan and history, `qa.json` as obligations plus assessments, and `verify/ledger.tsv` as separate property-check evidence. Do not duplicate these stores or edit the rendered scope as another specification.

## Construct and correct

Apply the Execute Scope direct rules or, for planned work, its `PLANNED.md` and the bundled contract tools as this workflow's construction protocol. Use `100x workbench execute <change-folder> preflight <task-id>` before a planned task. Verify current scope, task, QA and New Scope revisions; resolve paths inside the project and the task allowlist. The supervisor owns execution fields and audits actual writes. Workers must not run Git or roll back work; separately authorized supervisor Git operations are not part of RED/GREEN.

For implementation tasks, RED changes only mapped test files and must fail because the intended behavior is missing, not from syntax, import or environment failures. Freeze tests during GREEN, change only authorized production paths, rerun the same check and applicable smoke checks. Do not weaken assertions or skip required checks. Treat review corrections the same way; reconcile findings outside the approved scope before expanding it. For procedures with effects, record the start and result. After interruption, reconcile uncertain external effects using the original correlation reference before any retry.

Before and after every evidence check, use `100x workbench qa <change-folder> candidate --project-root <project-root>` and record that exact candidate with the check definition, effective environment and actual observations. Preserve start and result events in `tasks.json`. After all candidate-changing edits, check the final candidate; reuse evidence only when candidate, definition, QA revision, environment and isolation still match. Fingerprinting excludes the change folder, `.100x`, `.project-mapper`, Git metadata and dependency/cache folders except for declared task, check and source paths; source symlinks block this adapter. Before checks, identify exact generated build paths and declare them in `qa.json.contract.candidate_policy.generated_outputs`, never broadly exclude source. For checks using generated products, declare the actual files in `evidence_checks[].runtime_artifacts`; capture their digests before and after with QA Scope's `runtime-artifacts` command. The adapter cannot infer undeclared runtime dependencies or identify a running deployment or external services: capture and verify those separately. Save a local evidence artifact within the task's project root, normally in `.100x/`; for an external observation retain a local snapshot with its provenance. A missing or changed artifact or declared runtime product makes the affected blocking finding inconclusive.

Candidate v2 uses logical roots and is stable across equivalent checkouts; prior candidate IDs require a fresh run and assessment. QA Scope's `export-evidence` and `import-evidence` transport the contracts, cited artifacts and declared runtime products to an equivalent checkout without overwriting conflicting files. Map any external roots explicitly. The supervisor must freshly verify the effective environment; importing a bundle does not authenticate its author. Bundles can contain sensitive paths and file contents. See QA Scope for the commands and limitations. Execute preflight exposes `effective_project_path` after relocation while keeping the original task definition as provenance.

## Review and complete

Use the existing 100x reviewer and triage to assess the QA obligations and relevant additional defects in the same review. Inspect decisive artifacts, assertions, current source, candidate and effective environment. The reviewer cannot alter the published contract to approve a candidate. PASS requires demonstrated assertions; FAIL requires credible contradictory observations; INCONCLUSIVE covers missing, stale or unreliable evidence. Overall FAIL takes precedence for blocking failures, otherwise INCONCLUSIVE for blocking gaps, otherwise PASS. Report advisory findings as well. A property check's seeded-defect evidence is not automatically a task's implementation RED.

For a run requiring a 100x report, set `mode` to `engineering` and set `engineering` to a JSON object with `type` (`direct` or `planned`), `visual` (boolean) and, for headless work, `visualReason`. Direct work also records `evidence`; planned work records `changeId` and `environments`, an object keyed by `task-id/check-id` with the freshly observed environment identity for each blocking check. The supervisor must obtain those identities from the actual targets, not copy them blindly from the attempt. Record `title`, `pitch`, `verdict`, `verdictWhy` and `review` through `100x run set`. The reviewed state uses the existing review log and triage; an unavailable review is UNREVIEWED with a reason. For visual work retain the screenshot and resolution matrix. Headless work needs neither. `100x finish` calls the Python QA summary for planned work and checks structural bindings and completion; it cannot judge whether artifacts prove an assertion or independently verify caller-confirmed external environments. A blocking FAIL or INCONCLUSIVE cannot support a positive verdict, but can be reported with `dud` and its actual status. Direct reports state that no formal QA contract was used. Finish records an assessment snapshot, not a promise that later edits are covered.

Use property checking, seeded defects, independent review, visual capture, resumability and reports when they fit the task. Do not invent follow-up features, implement alternatives, add visual polish or repeat sufficient checks merely to consume a time budget. Explicit prototype and fill-time modes retain their own behavior.
