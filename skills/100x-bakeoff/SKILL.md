# Bake-off

Does the same agent make prototypes that a blind judge prefers when it follows the 100x-mockup skill, compared with the same agent without it? This skill runs that test and reports what came out, including when nothing could be shown. It builds no prototype of its own and never argues for the skill. Today it runs only through the Cursor SDK, because every arm and judge starts with `100x helper run`. Where that is not set up, step 1 says what to run, and nothing runs on a stand-in.

Two arms, `skill-off` and `skill-on`, make the same briefs under the same model and the same 20 minutes. Each pair is judged twice with A and B swapped, from folders that carry no arm name. The key that says which arm is which is sealed with a hash first, and the hash is signed with this machine's 100x key. The word is "ahead" only with at least 6 decisive pairs, an exact sign test under 0.05, and a judge that passed two controls. Otherwise it is "not shown", with the reason. The tool decides the word and you never do.

Done when `100x eval bakeoff score` has written `report.md`, the report sits in `docs/evals/` with a picture of each pair, and the reply carries the counts and the verdict line of `score` word for word, and every caution under it. A report that says "not shown" is a finished bake-off.

Messages to the owner follow `100x ref voice`: the answer first, one idea per line, one question last, every fact kept.

## Steps

1. The helper. `100x helper models` is the check: it lists the model ids, or says why it cannot. `The Cursor SDK is not installed. Run `100x helper setup` once.` means run `100x helper setup`. `The Cursor SDK has no valid login.` means run `100x helper login` once, which opens a browser to approve this machine, or set `CURSOR_API_KEY`. Run the one it names and `100x helper models` again, and do not go on until it lists models. When it still cannot, stop with the line it printed and the one step that is the owner's, which is the login. The pairs step photographs every page, so `100x eval bakeoff init` prints a Browsers line when no Chromium is installed. Run `100x browsers` before any arm starts, not after.
2. Read `evals/PROTOCOL.md` in the 100x repo. `100x eval bakeoff init` prints its path. It fixes the rule for the word and names the threats. Once an arm has started, change nothing in it. A change is an amendment at the bottom.
3. One model. The protocol wants the same model for every arm and judge, the one the owner's rules name, or the model this thread runs on when no rule names one, and the first line of the reply says which. Every arm and judge starts through the Cursor SDK with `100x helper run`, never with the Task tool and never with `cursor-agent`. `100x ref apps` says why. Use the id exactly as `100x helper models` lists it, with the effort and context the rule gives. A rule that names `muse-wonder-1.0-max`, for example, is `--model muse-wonder-1.0 --effort max --context 300k`. The window is always named and never 1m, because a 1m window or no window is MAX mode and `100x helper run` refuses it. Start one small helper first, `100x helper run --model <id> --effort <level> --context <size> --task "Reply with the word ok."`. Exit code 3 means the SDK reports another model. Stop, say so in one line, and give the owner the one decision. When the result reports no model, no receipt can be made from it, and the word is withheld for that run. Say so.
4. Folder. Somewhere neutral, never under `.100x` and never with `100x` in the path, because a judge sees its path. `100x eval bakeoff init <dir> --first 3 --pin` is the pilot, and no `--first` runs all twenty briefs, which is the run that can say "ahead". `init` prints what that costs in tokens and time and how many decisive pairs to expect, so say it to the owner before the first arm starts. `--pin` freezes the skill and tells the second arm to use it. `100x log` the seed, the folder and the pinned commit.
5. The arms, one helper at a time, in the order init printed. For each run:
   - `100x eval bakeoff mark <dir> <brief>/<arm> start`. Then start a fresh helper with `100x helper run --model <id> --effort <level> --context <size> --task-file <dir>/tasks/<brief>--<arm>.md --cwd <that run's folder, as `100x eval bakeoff status <dir>` prints it> --minutes 20 --receipt <dir>/helper-receipts/<brief>--<arm>.json --json`, with `block_until_ms` 0 in Cursor, and wait for its finished notice. It gets the text of that task file and nothing else, and it must not see the other arm, the protocol or this skill.
   - When it ends, `--minutes` has already stopped it at its deadline. Exit code 3 voids the run, and `modelCheck` says why. Then `100x eval bakeoff mark <dir> <brief>/<arm> stop --receipt <dir>/helper-receipts/<brief>--<arm>.json`. The receipt is the SDK's result in a file this machine's 100x key signed, and `mark` takes the model asked for, the model and settings that ran and the tokens from it. Never type them with `--ran`: a name typed by hand is counted as the helper's word, and the word "ahead" is not printed over it. The minutes come from the clock and never from what a helper says.
   - A run that ends with no `index.html` failed. Do not open the folder, do not write the page and do not start the run again. Go on to the next run.
6. `100x eval bakeoff pairs <dir>`. It builds the pairs and both controls, scans every judge folder for the skill's name and the arm names, seals the key and prints its hash. Log the hash now, before any judge starts. The scan reads what each file holds, whatever its name ends in, and searches a binary file for every name, except that a compressed picture is not searched for the four-letter `100x`. It reads `skill_on` and `skill- on` as the name, and `unreviewed` and `mockup` too, because a run may write them on its own page and a judge that reads them can tell the arms apart (five of the twenty pages in the 2026-11-21 run did, though the skill only asks for the label on the card and in the final message). Each task tells both arms to leave them off the page. A brief that is itself about a mockup lets `mockup` through with `--allow`. It refuses a symbolic link and a file over 25 MB, because it cannot check them. A page's title, its attributes and a picture that shows a name are not in the text it showed, so they pass. `--no-capture` runs no page at all, so a name a script builds in the browser passes too: use it for tests, and never for a run whose result will be quoted. When it refuses it names a file and a line. Remove only the words it names from that arm's folder, log each edit with its file and line, and run `pairs` again with `--edit "<file and what you removed>"` once for each. The key's scan record keeps the edits and `score` cautions about them, so the report says a person touched the pages. Say in the reply that the folders were edited. Nothing is built and no key exists until the scan passes.
   - When it names arm folders with no `index.html`, those runs failed and stay in the count. Run it again with `--blank-missing`. The judge gets a blank page in place of each, the arm's own folder is not touched, and the report names the runs. Log which runs they were.
7. The judges, one fresh helper for each folder under `<dir>/judge/`, one at a time, on the same model. Start each with `100x helper run --model <id> --effort <level> --context <size> --cwd <that folder> --minutes 30 --receipt <dir>/helper-receipts/<that folder's name>.json --json --task "Open this folder and follow ask.md in it."`. Do not say what the folders are for, which arm made which, or that a skill exists. Never point one at `<dir>`, `key.json` or `tasks/`. When each one is done, run `100x eval bakeoff mark <dir> judge/<that folder's name> stop --receipt <dir>/helper-receipts/<that folder's name>.json`. A judge record needs no start. `score` withholds the word unless every judge folder has one. Each judge's `ask.md` asks it to copy the start of the key's hash into its `verdict.json` as `sealed`. That is the proof the verdict came after the seal, and it survives a copy of the folder.
   - Never edit a `verdict.json`. A `why` that names an arm, a key or a skill, or says the judge looked elsewhere, voids that verdict. `score` withholds the word when a `why` holds a name it knows. Delete the file, log it, and judge that folder again with a fresh helper.
   - `100x eval bakeoff status <dir>` says when every verdict is in. While judges are left it adds a `Reach:` line. When that line says "ahead" can no longer be reached, even if every pair left went one way, stop judging, run `score`, and say in the reply that the judging stopped for that reason. A lead is never a reason to stop. The gallery needs every verdict, so an early stop commits `report.md` from `score` as `docs/evals/bakeoff-<yyyy-mm-dd>.md` instead.
8. `100x eval bakeoff score <dir>`. It refuses a key whose hash changed, and withholds the word when a verdict is missing or names an arm, when the judge failed a control, when the key was sealed after a verdict, when the model that ran is not on record for every arm run and every judge folder, when the arm runs or the judges did not all use one model at one setting, when a receipt does not back every record, or when the sealed key has no signature from this machine's key. A pair whose page carries `unreviewed` or `mockup` (a run made before the scan knew the words, or one that the scan let through with `--allow`) is set aside: the word is worked from the other pairs, the report prints the count of every pair beside it, and it says "not shown" when the rest are too few or too even. Score on the machine that built the pairs, because the signature does not travel, and anywhere else it prints a recount and says the signatures cannot be checked there. Exit code 2 means it withheld the verdict, and the screen lists each reason as a bullet. Do not quote "ahead" or commit a gallery after a 2. Read `report.md` whole, the limits too.
9. `100x eval bakeoff gallery <dir> --out docs/evals/bakeoff-<yyyy-mm-dd>` writes the report with a picture of each pair beside its result, arms labeled now that the judging is over. It refuses until every verdict is in, because it names the arms, and it exits 2 when the verdict was withheld. It prints a line for each picture, and `pairs` prints a line for each page it photographs, because both take minutes. Commit it. A number the owner reads comes from that file.

## Reply

Six lines at most. The counts line and the `Verdict:` line of `score` word for word first, with each caution bullet under them, then the one limit that matters most, then the minutes per arm, then the report path. When something could not run, say what and give the one decision that is the owner's. No other claim about the skill.

## Rules

- The tool's word is the only verdict. "Ahead" when the report says ahead, "not shown" otherwise, and never a softer or a stronger word. Print every p value as the tool gives it.
- Blind by instruction and by scan, not by construction. A judge is never told which side is which, never pointed at the key, and never given a second pair in the same helper.
- One helper at a time, one model for every arm and judge, and a model that did not run is not a run. Nothing is run on a stand-in without saying so in the first line.
- The same conditions for both arms. Only the second arm's task has a method paragraph.
- A failed run, a tie and a flip stay in the count. Dropping them is how a lead gets made up.
- No sound, no push, no prototype built here. The `100x-judge` skill is for a project's own review, and this skill never edits what an arm made beyond the words step 6 allows.
